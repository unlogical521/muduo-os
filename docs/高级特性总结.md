# muduo 项目高级特性与应用场景总结

> 本文档梳理 `reactor/`（多 Reactor 终版）中用到的**所有高级特性**及其**具体应用场景**。
> 按三大维度组织：① C++ 语言高级特性 ② Linux 系统编程/OS 特性 ③ 架构与并发设计模式。
> 每条都标注了代码位置（`文件:行号`），方便对照源码理解"为什么这么写"。

---

## 一、C++ 语言高级特性

### 1. 智能指针 + RAII（`unique_ptr` / `shared_ptr`）

**应用场景**：几乎每一个需要"持有资源且随作用域自动释放"的地方。

| 用法 | 位置 | 具体场景 |
|---|---|---|
| `std::unique_ptr<Channel>` | `EventLoop.h:111`、`TcpConnection.h:100`、`Acceptor.h:49` | 每个 fd 封装一个 Channel，Channel 析构时自动从 epoll 摘除（`Channel.cpp:11-17`），杜绝 fd 泄漏 |
| `std::unique_ptr<TimerQueue>` | `EventLoop.h:117` | 定时器队列生命周期随 EventLoop |
| `std::unique_ptr<Buffer>` | `TcpConnection.h:102-103` | 每个连接独立的输入/输出缓冲 |
| `std::make_shared<TcpConnection>` | `Server.cpp:97` | 连接对象交给 shared_ptr 管理 |
| `std::map<int, std::shared_ptr<TcpConnection>>` | `Server.h:107` | **连接表**：连接从建立到关闭的整个生命周期都靠它兜底，最后一个引用消失时才析构 |

**为什么高级**：网络库中 fd / epoll 注册 / 堆对象极易泄漏或双重释放，RAII 让"资源随对象析构自动清理"成为约定，`EventLoop::~EventLoop()`（`EventLoop.cpp:54-59`）与 `TimerQueue::~TimerQueue()`（`TimerQueue.cpp:36-44`）几乎不需要手写清理逻辑。

### 2. `enable_shared_from_this` + `shared_from_this()` —— 回调保活

**应用场景**：`TcpConnection` 继承 `enable_shared_from_this`（`TcpConnection.h:32`）。凡是"这个连接可能跨线程/异步执行，执行时对象必须还活着"的地方，都用 `shared_from_this()` 捕获自身：

- 跨线程 `send()`：`TcpConnection.cpp:66` 的 lambda `[self = shared_from_this(), msg]`
- 跨线程 `shutdown()`：`TcpConnection.cpp:122`
- 跨线程 `forceClose()`：`TcpConnection.cpp:145`
- 延迟关闭重入队列：`TcpConnection.cpp:169`

**为什么高级**：裸 `this` 捕获在异步回调里等于"悬垂风险"。`shared_from_this()` 相当于把对象**自己**变成了一个 shared_ptr 副本，保证回调执行期间对象必然存活——这是多线程网络库处理生命周期安全的**标准解法**（muduo 原著的做法）。

### 3. Lambda 表达式 + `std::function` 回调机制

**应用场景**：整个框架的"可扩展性"都建立在回调之上：

- `Channel` 的 4 个事件回调：`Channel.h:60-63`，构造时用 lambda 绑定 `[this]{ handleRead(); }`（`TcpConnection.cpp:29-32`、`Acceptor.cpp:45`、`EventLoop.cpp:43`）
- `EventLoop` 跨线程任务队列 `std::vector<Functor>`（`EventLoop.h:112`）
- `Timer` / `TimerQueue` 定时回调（`Timer.h:22`）
- `Server` 的 message / connection / close 回调（`Server.h:47-49`），demo 里用 lambda 直接写业务逻辑（`server.cpp:82-114`）

**为什么高级**：`std::function<void()>` 可以同时容纳 lambda、函数指针、绑定器，让"事件 → 回调"完全解耦，框架核心不感知业务；lambda 捕获（`[this]`、`[self = shared_from_this()]`、`[this, when, cb = std::move(cb)]`）又精准控制回调闭包的生命周期与数据搬运。

### 4. 移动语义 `std::move` —— 零拷贝传递

**应用场景**：

- 回调入队：`EventLoop.cpp:170` `pendingFunctors_.push_back(std::move(cb))`
- 定时器注册：`EventLoop.cpp:222,228,236` 把 `cb` 用 `std::move(cb)` 捕获进 lambda，再 `std::move(cb)` 传给 `addTimer`
- 回调设置：`setMessageCallback(MessageCallback cb) { messageCallback_ = std::move(cb); }`（`Server.h:68-71`）
- 线程名/名字构造：`EventLoopThread.cpp:11-12` `name_(std::move(name))`

**为什么高级**：回调对象（std::function 闭包）通常有堆分配，按值传+移动避免重复拷贝；`runInLoop` 里 `std::move` 还能让跨线程投递"只搬数据不复制"。

### 5. `= delete` 禁止拷贝 —— 明确所有权语义

**应用场景**：所有"有明确归属、不能被复制"的类都删除拷贝构造/赋值：

- `EventLoop`（持有 epoll fd、线程 id）：`EventLoop.h:53-54`
- `Channel`（一个 fd 只属于一个 loop）：`Channel.h:33-34`
- `TcpConnection`（一个连接对象唯一对应一个 socket）：`TcpConnection.h:48-49`
- `Acceptor`、`TimerQueue`、`EventLoopThread`（线程不可复制）、`Server`、`EventLoopThreadPool`

**为什么高级**：删除拷贝操作在编译期拦截"意外复制 fd / epoll 注册 / 线程"这类灾难性错误，是 C++11 起表达"不可拷贝资源类"的标准做法。

### 6. `thread_local` —— 每线程独立状态

**应用场景**：`EventLoop.cpp:14` `thread_local int t_loopCounter = 0;`，每个 loop 线程独立的计数器，用于日志区分线程。

**为什么高级**：`thread_local` 让"每线程一份"的状态无需加锁，天然隔离；这里是日志序号，若换成统计指标也能零成本按线程聚合。

### 7. `std::atomic` —— 无锁布尔标志

**应用场景**：`EventLoop.h:103` `std::atomic<bool> quit_`。`quit()`（`EventLoop.h:64`）可能被任意线程调用（析构、主线程退出），而 `loop()` 在自己的线程里循环读 `quit_`（`EventLoop.cpp:71`）。

**为什么高级**：`atomic<bool>` 保证"一个线程写、另一线程读"时无数据竞争（否则是 UB），且相对 mutex 开销几乎为零，适合这种"只置位不保护复杂状态"的场景。

### 8. `std::thread` + `std::mutex` + `std::condition_variable` —— 线程与同步

**应用场景**：

- `std::thread` 启动 sub-reactor：`EventLoopThread.cpp:33`
- 条件变量**等待子线程内 EventLoop 构造完成**：`EventLoopThread.cpp:39-42` `cond_.wait(lock, [this]{ return loop_ != nullptr; })`，配合 `threadFunc` 里的 `cond_.notify_one()`（`EventLoopThread.cpp:64`）
- `std::mutex` 保护跨线程队列 `pendingFunctors_`（`EventLoop.cpp:113`）与连接表 `connections_`（`Server.h:108`）
- `std::lock_guard<std::mutex>` 保证异常安全的临界区（`EventLoop.cpp:169`、`Server.cpp:108`）

**为什么高级**：`startLoop()` 必须先拿到子线程建好的 `EventLoop*` 才能投递任务——用条件变量而不是 `sleep`，精确且不浪费；`lock_guard` 让临界区退出（含异常路径）时自动解锁。

### 9. `std::chrono` 时钟抽象 —— 时间与超时

**应用场景**：

- 定时器统一用 `std::chrono::steady_clock`（单调时钟）：`Timer.h:27`、`TimerQueue.h:58`
- `runAfter` / `runEvery` 延迟与周期：`EventLoop.cpp:230,238` `std::chrono::steady_clock::now() + delay`
- 心跳空闲判定：`TcpConnection.h:68-70` `now() - last_active_ > timeout`，单位统一为 `std::chrono::milliseconds`
- 单调时间 → `timespec` 转换供 timerfd 使用：`TimerQueue.cpp:135-143`

**为什么高级**：`steady_clock` 不受系统时间调整（`date`/NTP）影响，定时器与超时判定不会因改时间而错乱；类型安全的时长避免了毫秒/秒混淆。

### 10. `enum class` 作用域枚举 —— 连接状态机

**应用场景**：`TcpConnection.h:42` `enum class State { kConnected, kDisconnecting, kDisconnected }`，配合延迟关闭流程在 `forceCloseInLoop()` 里流转（`TcpConnection.cpp:166-175`）。

**为什么高级**：`enum class` 不隐式转 int、不污染外层命名空间（要写 `State::kConnected`），比 C 风格 `enum` 更安全，是表达状态机的现代写法。

### 11. `std::set` 红黑树 + `std::pair` 复合排序 —— 定时器队列

**应用场景**：`TimerQueue.h:58` `using Entry = std::pair<std::chrono::steady_clock::time_point, Timer*>`，`timers_` 是一个按到期时间排序的 `std::set`：

- 增/删/查 O(logN)（`TimerQueue.cpp:59,83,99-108`）
- 每次只需看最早的 `begin()` 来设置 timerfd（`TimerQueue.cpp:57,121`）
- `pair` 用"时间 + 递增序号"双字段排序，**同刻到期的定时器也能区分先后、不冲突**（序号 `nextSeq_`：`TimerQueue.h:73`）
- `lower_bound` 一次取出所有已到期定时器：`TimerQueue.cpp:99`

**为什么高级**：红黑树是有序容器中"插入/删除/取最小"综合最优的数据结构，天然适合定时器"始终盯住最早到期者"的模型；`pair` 做排序键解决了"同时到期"的边界问题。

### 12. 结构化绑定 + 基于范围的 for —— 遍历容器

**应用场景**：

- `TimerQueue.cpp:40` `for (auto& [expiration, timer] : timers_)` 析构时释放所有 Timer
- `Server.cpp:159` `for (auto& [fd, conn] : connections_)` 遍历连接表取快照
- `benchmark/perf_client.cpp:215` `for (auto& v : results)` 汇总延迟

**为什么高级**：结构化绑定让 map 遍历免去 `.first` / `.second`，代码表达"我要的是什么"而非"容器里的结构"，可读性大幅提升。

### 13. 默认成员初始化 + 类型别名

**应用场景**：

- 默认成员初始化：`TcpConnection.h:98` `State state_{State::kConnected};`、`EventLoop.h:114` `bool callingPendingFunctors_ = false;`、`TimerQueue.h:73` `int64_t nextSeq_{0};`
- 类型别名：`EventLoop.h:46-47` `using Functor = std::function<void()>;`、`Server.h:47-49` 各回调别名

**为什么高级**：默认成员初始化让"每个构造函数都必须记得设置所有成员"成为历史，减少漏初始化的 UB；别名让 `std::function<void()>` 这种长类型可读、可复用。

### 14. `std::vector` 交换（swap）技巧 —— 锁优化

**应用场景**：`EventLoop.cpp:200-207` `doPendingFunctors()`：

```cpp
{
    std::lock_guard<std::mutex> lock(mutex_);
    functors.swap(pendingFunctors_);   // 锁只覆盖"换出"这一瞬间
}
for (auto& f : functors) f();          // 执行期间不持锁
```

**为什么高级**：把整队回调 swap 到局部变量再执行，**锁持有时间从"执行完所有回调"缩短到"一次 swap"**；执行期间其它线程还能继续入队，并行度最大化。这是消息队列/任务池中经典的"换出执行"范式。

## 二、Linux 系统编程 / OS 高级特性

### 1. epoll 事件驱动 + `data.ptr` 零查找派发

**应用场景**：事件循环核心。注册时用 `ev.data.ptr = ch` 直接存 `Channel*`（`EventLoop.cpp:112`），`epoll_wait` 返回后 `static_cast<Channel*>(events_[i].data.ptr)` **无需任何查找**直接拿到 Channel（`EventLoop.cpp:84`）。

**为什么高级**：
- 相比 select 的 O(n) 扫描、1024 fd 上限，epoll 是 O(1) 就绪通知，支撑上万连接；
- 相比用 `data.fd` 再查 map，`data.ptr` 省掉一次容器查找，是 C10K 场景下的关键优化；
- 事件数满容量自动翻倍扩容，避免频繁 realloc：`EventLoop.cpp:90-92`。

### 2. eventfd —— 跨线程唤醒原语

**应用场景**：`EventLoop.cpp:34` `::eventfd(0, EFD_NONBLOCK | EFD_CLOEXEC)` 创建内核计数器 fd，注册为 wakeup Channel。跨线程投递任务时写 1 唤醒（`EventLoop.cpp:181-185`），目标线程读走消费（`EventLoop.cpp:189-193`）。

**为什么高级**：eventfd 把"跨线程通知"也变成 fd，从而**与网络 IO 统一进 epoll 事件循环**——不引入信号/轮询/独立唤醒线程，是 `one loop per thread` 模型里"线程间传递"的基石。`EFD_NONBLOCK` 保证读写不阻塞，`EFD_CLOEXEC` 防 exec 泄漏。

### 3. timerfd —— 把定时器变成 fd

**应用场景**：`TimerQueue.cpp:23` `::timerfd_create(CLOCK_MONOTONIC, TFD_NONBLOCK | TFD_CLOEXEC)`，注册为 Channel 进 epoll。到期时 epoll 像普通 IO 一样返回可读，`handleRead()` 读走计数并触发所有到期回调（`TimerQueue.cpp:66-91`）。

**为什么高级**：
- **无独立定时线程、无锁**：定时器与网络 IO 共用一个事件循环；
- `CLOCK_MONOTONIC` + `TFD_TIMER_ABSTIME` 支持绝对时刻精确到 ns（`TimerQueue.cpp:127`），且不受系统时间修改影响；
- 每次只 `timerfd_settime` 到最早到期者，无定时器时自动 disarm（`TimerQueue.cpp:112-130`）。

### 4. accept4 —— 一次系统调用完成"接受 + 设属性"

**应用场景**：`Acceptor.cpp:86-87` `::accept4(accept_fd_, ..., SOCK_NONBLOCK | SOCK_CLOEXEC)`。

**为什么高级**：传统 `accept` + 单独 `fcntl` 设置非阻塞/close-on-exec 需要**两次系统调用**；`accept4` 一次搞定，且 `SOCK_CLOEXEC` 保证 `fork+exec` 子进程不会继承新连接 fd（防 fd 泄漏到子进程）。

### 5. readv 分散读（scatter-gather IO）

**应用场景**：`Buffer.cpp:23-53` `::readv(fd, vec, 2)`，两块目标：
- `vec[0]` = Buffer 当前可写区
- `vec[1]` = 栈上 64KB 兜底缓冲区

**为什么高级**：如果只用 `recv` 追加，Buffer 不够大就要多次系统调用。readv 一次调用读尽所有数据，超出 Buffer 的部分进栈上兜底再 `append`（`Buffer.cpp:43-51`），**大幅减少系统调用次数**，是 muduo 原著的高性能读路径。

### 6. 非阻塞 IO + `EAGAIN`/`EWOULDBLOCK` 错误处理

**应用场景**：

- 监听 fd / 连接 fd 全部 `SOCK_NONBLOCK`：`Acceptor.cpp:20,87`
- accept 循环以 `EAGAIN` 作为"没有新连接"的退出条件：`Acceptor.cpp:90-93`
- 写满内核缓冲区时 `write` 返回 `EAGAIN`，剩余数据转 buffer：`TcpConnection.cpp:88-91`
- timerfd / eventfd 都带 `TFD_NONBLOCK` / `EFD_NONBLOCK`，读取不阻塞

**为什么高级**：非阻塞 + epoll 才是事件驱动的完整形态——**任何 fd 上的操作绝不阻塞事件循环线程**，`EAGAIN` 作为"暂时不可用、稍后再试"的标准信号被统一处理。

### 7. 事件类型精细化：`EPOLLRDHUP` / `EPOLLHUP` / `EPOLLERR` / `EPOLLOUT`

**应用场景**：`Channel::handleEvent()` 按优先级分发（`Channel.cpp:37-65`）：
1. `EPOLLERR` → errorCallback（异步错误，如非阻塞 connect 失败）
2. `EPOLLIN` / `EPOLLPRI` / `EPOLLRDHUP` → 读/关回调（`EPOLLRDHUP` 表示对端关闭写端，**还能读走剩余数据**）
3. `EPOLLOUT` → 写回调（`handleWrite`）
4. `EPOLLHUP && !(EPOLLIN)` → 关回调（对端挂断但无数据可读，需避免与正常关闭重复处理，`Channel.cpp:62-64`）

**为什么高级**：一个 fd 可能同时就绪多种事件，所以用 `if` 而非 `else if` 逐个检查；对"关闭/挂断/错误"三种终结状态的区分，决定了优雅关闭流程（先读光数据再 close）能否正确执行。

### 8. `SO_REUSEADDR` 端口复用

**应用场景**：`Acceptor.cpp:29` `setsockopt(accept_fd_, SOL_SOCKET, SO_REUSEADDR, ...)`。

**为什么高级**：服务器重启时大量连接处于 `TIME_WAIT` 状态（主动关闭方要等 2MSL），若无此选项 `bind` 会报 "Address already in use" 失败。这是网络服务**热重启的必备配置**。

### 9. `shutdown(SHUT_WR)` 优雅半关闭

**应用场景**：`TcpConnection.cpp:132` `::shutdown(connfd_, SHUT_WR)`。

**为什么高级**：`close` 是直接断开（可能丢数据），`shutdown(SHUT_WR)` 只关闭写方向、仍可读——先发完缓冲区数据、等对端读完响应后再收尾，是"优雅关闭"的正确姿势（TCP 四次挥手语义）。

### 10. `epoll_create1` 替代 `epoll_create`

**应用场景**：`EventLoop.cpp:25`。

**为什么高级**：去掉了被忽略的 `size` 参数，接口更简洁；Linux 2.6.27+ 的标准做法。

## 三、架构与并发设计高级特性

### 1. Reactor 模式 + `one loop per thread`

**应用场景**：`EventLoop::loop()` 就是 Reactor 核心循环（`EventLoop.cpp:69-97`）：`epoll_wait` → 分发 → 执行 pending。每个线程一个专属 EventLoop（`EventLoopThread::threadFunc` 在栈上创建，`EventLoopThread.cpp:55`）。

**为什么高级**：把"事件循环"与"线程"绑死，**一个连接的所有 IO 永远在同一个线程执行**，天然免锁（连接级串行化），避免回调重入。

### 2. 主从 Reactor 多线程模型（多 Reactor）

**应用场景**：`Server` + `EventLoopThreadPool`（`Server.cpp:45-60`、`EventLoopThreadPool.cpp:26-50`）：
- **主 Reactor**（main 线程）：唯一 `accept`，通过 `getNextLoop()` round-robin 分发新连接（`Server.cpp:93-119`）
- **Sub Reactor**（线程池）：各自独立 epoll，只处理分给它的连接 IO，互不竞争

**为什么高级**：单 Reactor 单线程是瓶颈（accept 和 IO 抢一个线程）；多 Reactor 把"建立连接"和"处理数据"拆到不同线程组，既并行又可控（线程数有界，不随连接数增长），是 muduo 的核心卖点。

### 3. 关键约束：连接必须在所属 reactor 线程上创建

**应用场景**：`Server::onNewConnection` 通过 `ioLoop->runInLoop([...]{ make_shared<TcpConnection> ... })` 把创建动作**调度到目标 sub-reactor 线程**（`Server.cpp:96-118`）。

**为什么高级**：`TcpConnection` 构造时 `channel_->enableReading()` 会调 `epoll_ctl` 把 connfd 加进 sub-reactor 的 epoll 实例——**这个操作必须在持有该 epoll 的线程上做**。这个"为什么必须 runInLoop 创建连接"的细节，正是多 Reactor 实现最容易出错的地方。

### 4. `runInLoop` / `queueInLoop` —— 跨线程任务投递 + eventfd 唤醒

**应用场景**：
- `runInLoop`：本线程直接执行（零开销），异线程入队+唤醒（`EventLoop.cpp:151-157`）
- `queueInLoop`：入队 `pendingFunctors_`，若异线程或正在执行中则 `wakeup()`（`EventLoop.cpp:167-176`）
- 上层用法：跨线程 `send` / `shutdown` / `forceClose` 都走这条通道（`TcpConnection.cpp:60-70`）

**为什么高级**：这是"线程间消息传递"而非"共享内存 + 锁"——所有跨线程操作统一收敛到一个入口，规避锁竞争和死锁，是并发网络库的最佳实践之一。

### 5. `callingPendingFunctors_` 标志 —— 处理"唤醒信号已消费"竞态

**应用场景**：`EventLoop.cpp:173` 判断 `!isInLoopThread() || callingPendingFunctors_` 才 wakeup；标志由 `doPendingFunctors` 管理（`EventLoop.cpp:202,213`）。

**具体竞态**：`doPendingFunctors` 已把队列 swap 空但还没执行完时，另一线程入队新任务并 wakeup——此时 wakeup fd 上一轮已被读走，新任务要等到下一轮 epoll_wait。加此标志后，新任务会在**当前批次末尾再执行一次**（`EventLoop.cpp:161-166`），避免无谓延迟。这是教科书级的事件循环细节坑。

### 6. 延迟关闭状态机 —— 避免在回调栈内析构对象

**应用场景**：`forceCloseInLoop()`（`TcpConnection.cpp:166-175`）：
```
kConnected      → 置 kDisconnecting，重新入队（本次不关）
kDisconnecting  → 第二次进入：事件回调栈已退，handleClose 安全
```

**为什么高级**：`forceClose` 可能在用户消息回调内被调用（如"踢人"）。若直接 handleClose → 触发 Server erase → shared_ptr 归零 → **本对象在自身成员函数栈上被析构**，继续访问成员就是 UB。延迟关闭把真正的析构推迟到"当前回调栈退出之后"，是网络库防止"栈内析构"悬垂的标准解法。

### 7. 直写优先 + 缓冲兜底 —— 零拷贝小包发送

**应用场景**：`sendInLoop`（`TcpConnection.cpp:83-112`）：
- output buffer 为空 → 直接 `write(fd)`；一次写完则**零额外开销**
- 写不完/`EAGAIN` → 剩余入 buffer + `enableWriting` 关注 `EPOLLOUT`
- buffer 非空（有积压）→ 直接入 buffer 等 `handleWrite`

**为什么高级**：若每次 send 都入 buffer + enableWriting，小数据包至少要**多一次 epoll_wait 往返**才能发出。对多数业务消息（小包），直接写一次完成，延迟显著更低——性能敏感场景的典型取舍。

### 8. 心跳超时回收半开连接

**应用场景**：`Server::setHeartbeat` + `checkHeartbeats`（`Server.cpp:33-37,70-78`）：
- main reactor 上 `runEvery` 一个扫描定时器（`Server.cpp:52`）
- 每次遍历连接表快照，`conn->isIdle(timeout)`（距上次收到数据超时，`TcpConnection.h:68-70`）→ `forceClose()`
- `last_active_` 在每次 `handleRead` 时刷新（`TcpConnection.cpp:189`）

**为什么高级**：客户端**拔网线 / 进程崩溃**时 TCP 无法感知对端消失，连接永远占着 fd 和内存。心跳扫描基于"最近活跃时间"判定半开连接并强制回收，是生产环境的必备能力。

### 9. `shared_ptr` 快照遍历 —— 遍历期间并发关闭不悬垂

**应用场景**：`getAllConnections()`（`Server.cpp:155-164`）在锁内把连接表拷贝成 `vector<shared_ptr>` 返回，demo 的 `broadcast()` 遍历它并逐个 `conn->send()`（`server.cpp:50-55`）。

**为什么高级**：若返回裸指针/引用，遍历期间另一线程 `erase` 该连接会悬垂。返回 shared_ptr 快照，调用方持有期间对象必然存活；锁也只在拷贝瞬间持有，遍历本身无锁。

### 10. 细粒度加锁 —— 只锁跨线程临界区，IO 路径无锁

**应用场景**：
- 加锁：`pendingFunctors_` 队列（`EventLoop.cpp:169`）、`connections_` 连接表（`Server.cpp:108-110,147-149`）——只在**跨线程**访问处加
- 无锁：一个连接的所有 IO（handleRead/handleWrite/handleClose）都在所属 sub-reactor 线程内串行执行，**不需要任何锁**（`TcpConnection.h:12-14`）

**为什么高级**：多线程性能的核心不是"用锁"，而是"**尽量不产生共享**"。连接级 IO 无锁是本项目能在多核下高效的关键设计。

### 11. Buffer 指针式读写 —— 避免频繁内存分配

**应用场景**：`Buffer` 用 `read_index_` / `write_index_` 两个指针（`Buffer.h:88-90`），consume 后只移指针，空间后续复用；`retrieveAll` 才重置（`Buffer.h:43-46`）；不足时才 `resize` 扩容（`Buffer.h:62-66`）。

**为什么高级**：每个连接高频收发时，若每次都 realloc/拷贝会拖垮性能。指针滑动 + 惰性扩容让大部分读写在已分配内存上完成。

### 12. round-robin 负载均衡 + 可退化单线程

**应用场景**：`EventLoopThreadPool::getNextLoop()` 游标循环分配（`EventLoopThreadPool.cpp:58-70`）；`threadNum == 0` 时退化为单线程（`EventLoopThreadPool.cpp:45-49`）。

**为什么高级**：round-robin 实现最简单、分配最均匀（虽不感知负载）；支持 0 线程的退化模式让低负载场景不必空转线程池，一份代码覆盖两种模型。

### 13. 批量 accept（while 循环）—— 规避 LT 模式乒乓效应

**应用场景**：`Acceptor::handleRead`（`Acceptor.cpp:83-108`）用 `while` 一次性 accept 完所有已到达连接，直到 `EAGAIN`。

**为什么高级**：LT 模式下只要监听 fd 还有未 accept 的连接，epoll 就持续返回 `EPOLLIN`。若一次只 accept 一个，就会"忙等 → 处理 → 再忙等"乒乓，批量 accept 一次取完，减少 epoll_wait 次数。

## 结语

本项目几乎覆盖了**现代 C++ 高并发网络编程的完整武器库**：

- **语言层**：RAII 智能指针、回调机制、移动语义、原子量、条件变量、`enable_shared_from_this`、单调时钟；
- **OS 层**：epoll + eventfd + timerfd + accept4 + readv，把"IO、唤醒、定时"统一抽象成 fd 纳入一个事件循环；
- **架构层**：主从 Reactor、one loop per thread、跨线程消息传递、延迟关闭、心跳回收、锁粒度优化。

每个特性都不是炫技，而是对应一个**具体的工程问题**（延迟、并发、悬垂、半开连接、系统调用次数）——这也是本仓库作为"从零实现网络库"学习项目最大的价值。
